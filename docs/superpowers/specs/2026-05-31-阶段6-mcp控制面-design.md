# 设计：阶段 6 — MCP 控制面（外部总控）

日期：2026-05-31
状态：已与用户确认（全包 6a+6b+6c），待转实现计划
关联：PRD v2 §11（docs/PRD_v2_万能节点工作台与管家总控.md）

## 背景与动机

内置总控已移除（见 2026-05-31-移除内置总控与统一凭证）。本阶段让外部 agent
（Claude Code / Codex）作为**外部总控**操控工作台：编排、运行、看过程、看产物、
诊断、随时造节点——实现真正的"运行层指哪打哪"，并能在画布上实时看到操作过程。

当前"指哪打哪"只通了**建设/编辑层**（外部 agent 直接改工程文件）；**运行/操控层**
未通：没有 MCP 通道，且运行引擎 `RuntimeEngine` 绑死 PyQt 信号与 Qt 事件循环，
DAG 编排逻辑还散落在 `main_window`（`_run_chain/_start_ready_nodes`）。

## 目标

1. 抽出无 Qt 的执行核 `WorkflowRunner`，GUI 与 MCP 共用一套编排/执行。
2. MCP server 暴露编排/运行/造节点工具，Claude Code 可经 stdio 接入操控工作流。
3. `workflows/active.json` 作单一真相源；PyQt 画布监听并实时重绘（看过程）。
4. 保留安全闸门：高风险真实动作需显式确认；不暴露凭证；造节点默认预览。

## 非目标

- 不改变节点能力与凭证机制（沿用 `ToolExecutor` / `{cred:}`）。
- 不做多用户/网络化（MCP 仅本机 stdio）。
- 不做复杂并发锁（单人迭代场景，用 `rev` 守卫即可，YAGNI）。

## 决策记录（与用户确认）

| 决策 | 选择 |
|------|------|
| 本轮范围 | **全包 6a+6b+6c** |
| 执行核 | **统一**：抽 `WorkflowRunner`，GUI 跑流程改走它（方案 A）|
| 单一真相源 | `workflows/active.json` + `rev` 自增号 |
| GUI 同步 | `QFileSystemWatcher` 监听，`rev` 比对触发重载，避免回环 |
| 并发 | 不上重锁，`rev` 守卫 |
| 安全 | 高风险真实节点返回 `needs_confirmation`，需 `confirm=true` 再执行 |
| 造节点 | 默认 `write=false` 预览，`write=true` 落盘 |

## 架构

```text
Claude Code / Codex ──stdio──> MCP server (app/mcp/server.py，薄壳)
                                   │ 调用
                                   ▼
                          app/mcp/store.py（工作流仓库：active.json 读写 + rev + 编排操作纯函数）
                                   │ 运行
                                   ▼
                          app/runtime/runner.py（WorkflowRunner，无 Qt）
                                   └─ ToolExecutor（已有，纯 Python）
                                   ▲
                      workflows/active.json（单一真相源，带 rev）
                                   ▲ 监听重绘
                          PyQt 画布（GUI 改走 Runner + 监听 active.json）
```

## 组件设计

### 1. WorkflowRunner（app/runtime/runner.py，无 Qt）

把现散在 GUI 的 DAG 编排抽成纯 Python：

- 输入：`nodes`（WorkflowNode 列表）+ `edges`（WorkflowEdge 列表）。
- `run(start_ids=None)`：算依赖、无依赖节点优先、上游产物喂下游；`执行模式=真实`
  走 `ToolExecutor.execute`，否则产出 mock 输出（沿用现有 mock 样例）。
- 失败阻断依赖它的下游，但不影响无关节点。
- **进度回调** `on_progress(node_id, status, output_or_error)`：Qt-free，
  GUI 适配器接成 Qt 信号重绘；MCP 接成写回 active.json + 日志。
- 真实执行可在后台线程；提供同步 `run_sync` 供 MCP/测试使用。
- mock 编排逻辑从 `engine.py`/`main_window` 迁入；`engine.py` 的 GUI 适配收敛为
  "用 Runner + 回调转 Qt 信号"的薄层。

### 2. 工作流仓库 store（app/mcp/store.py，无 Qt，纯函数为主）

以 `workflows/active.json` 为真相源，结构沿用现有 workflow 保存格式 + `rev`：

```json
{ "version": "0.1.0", "rev": 12, "nodes": [...], "edges": [...] }
```

函数（均可单测，操作显式 path，默认 active.json）：

- `load_workflow(path) -> dict` / `save_workflow(data, path)`（写时 `rev+1`，返回新 rev）。
- `add_node(type, params, x, y)` → node id；`connect(src, tgt)`（`best_connection` 校验）；
  `set_params(id, params)`；`delete_node(id)`。
- `get_workflow()`；`get_output(id)`；`run(start_ids, confirm) -> 结果`（构造
  WorkflowNode/Edge → WorkflowRunner.run_sync → 把 status/last_output 写回）。
- `needs_confirmation` 判定：节点 `requires_confirmation` 且 `执行模式=真实` 且未
  在 `confirm` 放行列表 → 返回待确认，不执行。

### 3. MCP server（app/mcp/server.py，薄壳）

用 MCP Python SDK（FastMCP，stdio）。每个工具仅做参数校验 + 调 store/runner/
node_builder，返回结构化结果：

`list_nodes` / `get_workflow` / `add_node` / `connect` / `set_params` /
`delete_node` / `run_node` / `run_chain` / `run_all` / `get_output` / `get_logs` /
`create_skill_node(skill_file, mode, instruction?, write=false)` / `reload_nodes`。

资源：`workflows/active.json`、`runs/*.log`。安全：见下。

### 4. GUI 同步（app/ui/main_window.py）

- 启动加载 `workflows/active.json`；所有 GUI 改动写回 active.json（autosave）并记下
  自己写的 `rev`。
- `QFileSystemWatcher` 监听 active.json；变化时若文件 `rev` > 自记 rev（外部=MCP 改的），
  防抖后重载场景重绘。
- GUI 跑流程改走 `WorkflowRunner`（经回调更新节点状态/画布），与 MCP 行为一致。

## 安全（6c）

- 高风险真实节点：`run_*` 返回 `needs_confirmation`（含节点名/风险等级），
  需 agent 显式 `confirm=true`（或 `confirm=[node_ids]`）再调一次才执行。
- MCP 仅本机 stdio，无网络端口。
- 不暴露凭证：无读 credentials 工具；`{cred:}` 仅在脚本子进程注入，MCP 不回传密钥。
- 造节点默认 `write=false` 预览。

## 数据流（示例：你说"给文章配图出图传公众号"）

1. agent `create_skill_node`/`add_node` 拼出节点 → 写 active.json（rev+1）→ 画布重绘。
2. `connect` 串链路（端口校验）→ 写 → 重绘。
3. `run_chain(confirm=...)` → WorkflowRunner 跑 → 状态/产物写回 active.json → 画布
   实时显示运行/成功/失败；高风险节点返回待确认。
4. `get_output` 读产物路径回报给你。

## 错误处理

- 端口不兼容 connect → 返回契约级原因（复用 `describe_port`）。
- 节点失败 → status=failed + error 写回；下游阻断；`get_logs` 可查。
- active.json 损坏/并发 rev 冲突 → store 以磁盘为准重载，返回冲突提示。

## 测试

- `tests/test_runner.py`：依赖排序、下游等上游、mock 跑、产物传递、失败阻断、无依赖并行。
- `tests/test_mcp_store.py`：add/connect(校验)/set/delete/run 在临时 active.json 往返；
  `rev` 自增；`needs_confirmation` 闸门；`create_skill_node` 预览 vs 落盘。
- GUI 同步（offscreen）：active.json `rev` 变化触发画布重载；GUI 自身写不触发回环。
- 依赖：`uv pip install mcp`。
- 本机无 pytest，沿用临时 runner 调 `test_*`；真实解释器 Python313。

## 验收标准

1. Claude Code 经 `.mcp.json` 连上 workbench MCP，`list_nodes` 能拿到全部节点。
2. 经 MCP 工具搭出"文章→配图→出图→上传公众号"链路、`run_chain` 触发运行、
   `get_output`/`get_logs` 读到产物与日志。
3. 上述操作在 PyQt 画布上**实时可见**（节点出现/连线/状态变化）。
4. 高风险真实节点不经 `confirm=true` 不执行。
5. `create_skill_node` 可预览并（write=true 时）入库即用。
6. WorkflowRunner / store 单测通过；GUI 与 MCP 共用一套执行核。
