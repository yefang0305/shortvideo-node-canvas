# PRD：短视频节点画布工作台

## 1. 产品定位

短视频节点画布工作台是一款本地桌面端的短视频自动化编排工具。它把现有的采集、下载、ASR、文案处理、批量混剪、自动发布等能力拆成一个个可拖拽节点，用户可以在无限画布上独立运行节点，也可以通过连线把多个节点组合成自动化流程。同时，它内置一个大模型总控助手，用户可以通过聊天描述目标，由总控助手生成计划、编排节点、调度执行并辅助处理异常。

它不是通用版 n8n，也不是简单工具箱，而是面向短视频生产场景的垂直 Agent 工作流引擎。

一句话定位：

> 像 n8n / Coze 一样拖拽编排，但专门服务短视频采集、生产、发布全流程；每个节点既是独立工具，也是工作流组件，并可被大模型总控调度。

## 2. 背景与机会

当前已有多个独立能力：

- 抖音主页作品链接采集
- 抖音视频下载
- 本地 ASR 口播文案提取
- 文案改写、标题生成
- 批量混剪生成
- MediaPush 多账号自动发布
- 发布记录核验、失败补发
- 大模型计划、编排和异常处理

这些能力已经能组成完整生产链路，但目前更像分散的工作台或项目。用户需要理解每个工具的入口、参数、输入输出文件，并手动衔接流程。

如果把它们节点化，可以形成一个更强的产品叙事：

- 从“功能集合”升级为“自动化系统”
- 从“我有很多工具”升级为“我能设计工作流平台”
- 从“单点效率提升”升级为“全链路短视频生产流水线”
- 从“人手动配置流程”升级为“Agent 理解目标并调度工具”

## 3. 目标用户

### 3.1 第一目标用户

独立短视频运营者、矩阵号运营者、内容工作室负责人。

他们关心：

- 批量采集对标内容
- 快速提取脚本
- 自动生成多个视频版本
- 多账号定时发布
- 失败任务可追踪、可重试

### 3.2 第二目标用户

开发者、自动化工具爱好者、AI 工具产品观察者。

他们关心：

- 节点画布是否直观
- 工具能力是否可扩展
- 项目结构是否清晰
- 是否能作为 GitHub 项目展示技术能力

## 4. 产品目标

### 4.1 MVP 目标

第一版目标不是做完整 n8n，而是做出一个可运行、可演示、有产品感的本地节点工作台。

MVP 必须做到：

- 打开程序后进入无限画布
- 左侧可以看到短视频业务节点库
- 节点可以添加到画布
- 节点可以拖拽移动
- 节点之间可以连线
- 每个节点可以独立配置、独立运行
- 多个无依赖节点可以在画布上同时运行
- 两个节点相连时，上游输出可以作为下游输入
- 选中节点后可以在右侧编辑参数
- 可以保存和加载流程
- 可以运行单个节点、从某个节点继续运行、运行整条流程
- 节点运行时显示状态、日志和结果摘要
- 节点运行完成后保留最近一次输出，供后续节点复用
- 内置总控助手聊天入口
- 总控助手可以根据用户目标生成执行计划
- 总控助手可以建议或创建节点编排草图
- 总控助手可以读取节点结构化错误并给出修复建议

### 4.2 非目标

MVP 不追求以下能力：

- 不做多人协作
- 不做云端执行
- 不做完整插件市场
- 不做复杂表达式系统
- 不做任意第三方 API 接入
- 不做完全自由的通用自动化平台
- 不要求第一版所有节点都真实跑通全量业务
- 不做完全无确认的自动驾驶
- 不允许大模型绕过节点协议直接任意操作本地文件
- 不让大模型自动执行高风险动作，如账号登录、发布内容、删除文件

## 5. 核心场景

### 5.1 对标账号采集到文案库

用户输入一个抖音主页链接，流程自动完成：

1. 提取主页下所有作品链接
2. 批量下载视频
3. 对视频执行 ASR
4. 导出文案 Markdown 或文本库

### 5.2 文案到批量混剪视频

用户导入一批文案，流程自动完成：

1. 文案改写或清洗
2. 标题生成
3. TTS 语音生成
4. 素材随机匹配
5. BGM 混合
6. 字幕烧录
7. 批量导出视频

### 5.3 视频生成到自动发布

用户选择输出视频目录，流程自动完成：

1. 扫描待发布视频
2. 匹配账号组
3. 设置标题和发布时间
4. 调用 MediaPush 发布
5. 记录发布状态
6. 对失败任务进行重试或人工核验

### 5.4 Agent 总控调度

用户不手动画流程，而是在总控助手里描述目标：

> 帮我采集这个抖音主页，下载最近 30 条视频，提取口播文案，并筛出适合混剪的内容。

总控助手需要完成：

1. 理解用户目标
2. 生成可读的执行计划
3. 选择需要的节点
4. 自动在画布上创建节点并连线
5. 填入可推断的参数
6. 标出需要用户补充或确认的参数
7. 用户确认后调度节点运行
8. 运行失败时读取错误信息，提出修复建议或重试方案

MVP 中，总控助手默认是“辅助驾驶”而不是“自动驾驶”。涉及重任务、账号发布、文件覆盖、批量下载等动作时，需要用户确认后执行。

## 6. MVP 节点设计

### 6.1 抖音主页采集节点

用途：输入抖音主页链接，输出作品链接列表。

主要参数：

- 主页链接
- 最大采集数量
- 是否去重
- 导出文件路径

输出：

- 作品链接列表
- Markdown 链接文档

### 6.2 抖音视频下载节点

用途：输入作品链接列表，批量下载视频。

主要参数：

- 链接来源：上游节点 / 手动输入 / 文件导入
- 保存目录
- 并发数
- 是否跳过已下载
- CR TubeGet 运行目录

输出：

- 本地视频文件列表
- 下载成功/失败统计

### 6.3 ASR 文案提取节点

用途：输入视频或音频文件，提取口播文案，并把下游正式可用产物收敛为纯文本 TXT。

主要参数：

- 输入文件或目录
- ASR 模式：本地模型 / 火山引擎
- 是否启用过滤器
- 是否调用 LLM 优化错别字与断句
- 输出格式：TXT 纯文案
- 输出目录

输出：

- `clean_scripts`：纯口播文案 `.txt` 文件列表
- 调试副产物：`.md/.json` 可保留在输出目录，但不作为节点连线输出

### 6.4 文案改写与标题生成节点

用途：对提取文案进行清洗、改写，并生成短视频标题。

主要参数：

- 改写风格
- 改写 SKILL 文件
- 标题规则
- 大模型配置
- 输出数量

输出：

- 改写文案
- 标题
- 封面重点词
- `batch_scripts`：可供混剪使用的任务 JSON

### 6.5 批量混剪节点

用途：根据文案、素材库、BGM、字幕样式批量生成视频。

主要参数：

- 文案来源
- TTS API 配置
- 音色、语速、音量
- 分段模式与最短分段秒数
- 视频素材目录
- BGM 文件与音量
- 输出分辨率、帧率
- 输出目录
- 生成数量
- 封面底图

输出：

- 成品视频列表
- 生成日志
- 失败任务列表

### 6.6 MediaPush 发布节点

用途：把成品视频加入发布队列，并调用 MediaPush 完成发布。

主要参数：

- 视频目录
- 账号组
- 发布时间规则
- 标题来源
- 是否失败重试

输出：

- 发布记录
- 成功/失败统计
- 需要人工核验的任务

## 7. 画布交互设计

### 7.1 主界面布局

主界面分为三部分：

- 左侧：节点库
- 中间：无限画布
- 右侧：参数面板 / 运行日志 / 流程信息

底部可以放轻量状态栏，显示当前流程是否保存、当前运行状态、任务数量。

视觉风格以已确认的 HTML 预览稿为准：

- 深色桌面软件界面
- 左侧紧凑节点库
- 中间网格无限画布
- 节点卡片采用 8px 以内圆角、清晰状态徽标和端口
- 右侧为参数、运行、流程信息三类面板
- 整体偏专业工具感，避免营销页、卡片堆叠或过度装饰

### 7.2 节点库

节点库按业务分组：

- 采集
- 下载
- 文案
- 生成
- 发布
- 工具

MVP 可以先使用固定节点，不做自定义节点创建。

### 7.3 节点卡片

每个节点卡片需要展示：

- 节点名称
- 节点类型图标
- 简短状态
- 输入端口
- 输出端口

节点状态：

- 未运行
- 等待中
- 运行中
- 成功
- 失败
- 跳过

### 7.4 连线规则

MVP 只支持从输出端口连到输入端口。连线的含义是数据依赖和输入来源绑定，不代表一连接就立即自动运行。

第一版可以先做弱校验：

- 文本列表可以接下载节点
- 视频文件列表可以接 ASR 节点
- 文案列表可以接改写节点或混剪节点
- 视频文件列表可以接发布节点

类型不匹配时，连线可以失败并给出提示。

默认规则：

- 没有连线的节点可以作为独立工具运行
- 有上游连线的节点默认优先使用上游输出作为输入
- 如果节点同时配置了手动输入和上游输入，右侧参数面板需要显示当前输入来源
- 第一版允许用户手动切换为“使用手动输入”
- 连线后不自动触发下游运行，自动级联运行作为后续开关能力

### 7.5 参数面板

选中节点后，右侧显示该节点参数。

参数类型包括：

- 文本输入
- 文件选择
- 目录选择
- 数字输入
- 下拉选择
- 开关

MVP 不需要做复杂表单联动。

### 7.6 节点运行入口

每个节点卡片或右侧参数面板需要提供独立运行入口。

MVP 建议提供三种运行方式：

- 运行当前节点：只执行当前节点，不触发下游
- 从这里继续运行：执行当前节点，并按连线继续执行下游节点
- 运行全部流程：执行当前画布内所有可运行节点和流程片段

对于没有依赖关系的多个节点，系统允许它们并行运行。对于存在依赖关系的节点，下游节点必须等待上游节点成功完成并产出有效输出。

### 7.7 画布多任务状态

画布允许同时存在多个运行中的节点或流程片段。

界面需要能区分：

- 当前选中的节点
- 当前正在运行的节点
- 已成功完成的节点
- 失败等待处理的节点
- 等待上游输出的节点

右侧运行面板需要支持查看当前节点日志，也需要能切换到画布级运行日志。

## 8. 工作流执行模型

### 8.1 基础执行规则

画布执行模型以“节点独立运行 + 连线数据传递”为核心。节点不是只能存在于一条完整流程里，每个节点都可以作为单独工具运行。

当用户运行单个节点时：

1. 读取该节点参数
2. 如果存在上游输入且当前输入来源设置为上游，则读取上游最近一次输出
3. 执行当前节点
4. 保存当前节点输出和日志
5. 不自动触发下游节点

当用户选择“从这里继续运行”或“运行全部流程”时，根据节点连线生成有向无环图。

执行顺序：

1. 找到没有上游依赖的节点
2. 执行节点；互不依赖的节点可以并行执行
3. 将输出传给下游节点
4. 下游依赖满足后继续执行
5. 某个节点失败时，默认阻断依赖它的下游节点，但不影响无关节点继续运行

MVP 可以先限制不支持循环。

### 8.2 并行与依赖规则

并行规则：

- 没有连线关系的节点可以同时运行
- 属于不同流程片段的节点可以同时运行
- 同一个节点同一时间只允许一个运行实例，避免输出被覆盖
- 重任务节点需要显示排队、运行、取消、失败状态

依赖规则：

- 下游节点默认等待全部必需输入满足后才能运行
- 可选输入缺失时允许继续运行，但需要在日志中记录
- 如果上游节点没有成功输出，下游节点不能自动运行
- 如果上游输出已缓存，下游节点可以直接使用缓存运行

### 8.3 节点输入输出

每个节点统一使用结构化输入输出。

建议基础结构：

```json
{
  "type": "video_files",
  "items": [],
  "meta": {},
  "source_node_id": "node_xxx"
}
```

每个节点需要保留最近一次输出，输出缓存用于：

- 下游节点读取
- 用户查看结果摘要
- 改线后复用结果
- 失败后从中间节点继续运行

输出缓存不等于永久数据归档。涉及视频、文案、发布记录等大文件时，节点输出应保存文件路径、统计信息和元数据，而不是把大文件内容写入 workflow JSON。

### 8.4 运行状态

运行流程时，需要记录：

- 当前执行节点
- 每个节点开始时间
- 每个节点结束时间
- 标准日志
- 错误信息
- 输出摘要
- 节点输出缓存位置
- 节点是否由用户手动运行、上游触发、整条流程运行触发

MVP 可先把日志写入本地 `runs/` 目录。

## 9. Agent 总控设计

### 9.1 总控定位

Agent 总控是画布之上的大模型调度层。它不替代节点，也不直接绕过节点执行底层代码，而是通过统一节点协议理解工具能力、生成计划、配置节点、调度运行和解释错误。

核心原则：

- 大模型负责理解意图、拆解任务和调度节点
- 节点负责真实执行具体工具能力
- 画布负责可视化呈现节点、连线、状态和日志
- 用户保留关键动作确认权

### 9.2 总控入口

界面上需要提供一个总控助手聊天面板。

MVP 可以放在右侧面板的独立 Tab，或作为底部可展开抽屉。它需要支持：

- 用户输入自然语言目标
- 显示大模型生成的任务理解
- 显示建议执行计划
- 显示需要创建的节点和连线
- 显示缺失参数清单
- 用户确认后应用到画布
- 节点运行失败时展示原因和建议动作

### 9.3 节点协议

为了让 Agent 能调度节点，每个节点必须声明自己的机器可读能力。

节点声明至少包含：

- 节点类型
- 节点名称
- 能解决的问题
- 必需输入
- 可选输入
- 参数 schema
- 输出类型
- 错误码
- 是否属于高风险动作
- 是否需要用户确认

示例：

```json
{
  "type": "douyin_video_download",
  "name": "抖音视频下载",
  "capability": "download_douyin_videos",
  "inputs": ["profile_links"],
  "outputs": ["video_files"],
  "requires_confirmation": true,
  "risk_level": "medium"
}
```

### 9.4 Agent 调度流程

总控助手处理用户目标时，按以下流程运行：

1. 解析用户目标
2. 匹配可用节点能力
3. 生成计划草案
4. 检查缺失参数
5. 生成节点图草案
6. 请求用户确认
7. 创建或更新画布节点
8. 调用运行引擎执行
9. 观察节点输出和错误
10. 生成下一步建议

第一版不要求 Agent 自己无限循环解决问题。每轮失败后，Agent 应给出明确建议，由用户选择是否重试、改参数、跳过或停止。

### 9.5 安全边界

总控助手需要明确安全边界：

- 默认不能删除文件
- 默认不能覆盖已有输出目录
- 默认不能自动发布视频
- 默认不能自动登录账号
- 默认不能绕过平台风控或验证码
- 默认不能读取节点协议以外的敏感文件
- 批量下载、批量生成、批量发布前必须用户确认

### 9.6 MVP 能力边界

MVP 中 Agent 总控需要做到：

- 支持配置大模型 API Key 和模型名
- 支持聊天输入目标
- 支持生成执行计划
- 支持基于节点协议推荐节点
- 支持把计划转成画布节点草图
- 支持标记缺失参数
- 支持用户确认后创建节点和连线
- 支持读取结构化错误并给出建议

MVP 暂不要求：

- 完全自主执行长流程
- 自动处理所有异常
- 自动修改节点代码
- 自动绕过登录和风控
- 多轮复杂记忆系统
- 通用插件市场

### 9.7 与工作流引擎的关系

工作流引擎仍是确定性执行层。Agent 不能跳过运行引擎直接调用工具。

推荐关系：

```text
用户意图
  -> Agent 总控
  -> 节点计划
  -> 画布节点与连线
  -> 工作流运行引擎
  -> 节点执行器
  -> 结构化输出 / 错误
  -> Agent 解释与下一步建议
```

## 10. 保存格式

流程应保存为 JSON 文件。

保存内容：

- 流程名称

## 12. 与现有工具的关系

本项目应作为独立项目存在，不修改原有工作台。

第一阶段可以通过三种方式接入现有能力：

1. 复制已拆分工具的核心代码到本项目
2. 通过命令行调用已拆分工具
3. 节点先模拟运行，后续逐步替换为真实执行器

推荐 MVP 使用第三种和第二种结合：

- 先把画布、节点、连线、运行状态跑通
- 对已经独立稳定的工具，用命令行方式接入
- 对复杂模块先保留为占位执行器

## 14. 风险与应对

### 14.1 画布交互复杂

风险：节点拖拽、连线、缩放、选择等交互容易越做越复杂。

应对：MVP 只做必要交互，不做高级动画和复杂快捷键。

### 14.2 真实节点接入成本高

风险：每个旧工具输入输出不统一，直接接入会拖慢 MVP。

应对：先定义统一节点协议，用模拟执行器跑通，再逐步替换真实执行器。

### 14.3 工作流引擎膨胀

风险：容易扩展到条件、循环、变量、表达式等复杂能力。

应对：第一版只支持有向无环图，不支持循环和复杂表达式。

### 14.4 本地依赖重

风险：FFmpeg、CR TubeGet、ASR 模型、浏览器自动化等依赖会让项目配置复杂。

应对：README 中明确依赖检查；程序内提供环境检测面板作为后续功能。

### 14.5 Agent 行为不可控

风险：大模型可能误解用户目标、生成错误参数，或建议执行高风险动作。

应对：Agent 只能通过节点协议调度工具；重任务和高风险动作必须用户确认；错误处理以建议为主，不做无限自动重试。

## 16. 第一版验收标准

- 用户能保存和加载流程

- 用户能同时运行多个无依赖节点

- 至少一个真实节点成功接入
- README 能让别人理解项目价值和运行方式
